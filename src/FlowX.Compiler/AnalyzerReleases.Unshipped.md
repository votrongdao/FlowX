; Analyzer release tracking. Roslyn's RS2007/RS2008 rules require every diagnostic
; to be listed here before it can be raised, which makes adding, changing or removing
; a rule a reviewable diff rather than something that appears in someone's build one
; morning. Constraint C7 says the public surface is a forever commitment; a diagnostic
; id is part of that surface, because teams write suppressions against it.
;
; On release, these move to AnalyzerReleases.Shipped.md under a version heading.

FLOWX1047 | FlowX | Error | Data subject is declared where the runtime cannot record it — a [Subject] marker on more than one member of the input contract, on the output contract, on a member that is not a string, or on a flow that is not Durable. Each shape leaves the handle unwritten, so the rows can never be found by an erasure and cannot be repaired later: the identifier the handle would be computed from is redacted on the way in. FLOWX1045 | FlowX | Error | Schedule jitter cannot be read — a [CronTrigger] whose Jitter is not a positive ISO-8601 duration. The value is the window one firing is released within, derived from the firing so that every node releases it at the same instant; an unreadable or non-positive one is thrown on by FlowSchedule.Create at composition time, so the deployment finds out from a pod that never becomes ready rather than from a build that stops. [Documentation](https://github.com/votrongdao/FlowX/blob/master/docs/diagnostics/FLOWX1045.md)
FLOWX1042 | FlowX | Error | Stream-triggered flow cannot be windowed — a [StreamTrigger] on a flow whose input contract is not StreamWindowBatch, which a closed window has nothing else to give, or on a flow that is not Streaming, whose instances nothing journals and for which the window-derived instance id of ADR-0055 is therefore inert, or with a window this engine does not implement: tumbling is the only shape, because a sliding or session window's bounds are not a function of the event time alone and a global window is never closed by a watermark. [Documentation](https://github.com/votrongdao/FlowX/blob/master/docs/diagnostics/FLOWX1042.md)
FLOWX1048 | FlowX | Error | Triggers on one flow require different input contracts — a trigger that carries a body fixes what the flow's input contract is, and [CronTrigger] (ScheduledFire), [BusTrigger]/[KafkaTrigger]/[ChangeTrigger] (BusMessage) and [StreamTrigger] (StreamWindowBatch) do not agree, so two of them on one class cannot both be served. Reported instead of FLOWX1038, FLOWX1039, FLOWX1041 and FLOWX1042, each of which would otherwise tell the author to declare the contract that re-raises another. [Documentation](https://github.com/votrongdao/FlowX/blob/master/docs/diagnostics/FLOWX1048.md)
FLOWX1046 | FlowX | Warning | Agent tool declares no confirmation over declared side effects — [AgentTrigger(Confirmation = ConfirmationMode.Never)] on a flow whose steps reach a capability declaring SideEffects, so the tool descriptor publishes confirmationRequired: false for a call with a consequence, no client prompts, and a server running ConfirmationPolicy.Elicit has nothing to enforce. [Documentation](https://github.com/votrongdao/FlowX/blob/master/docs/diagnostics/FLOWX1046.md)
FLOWX1043 | FlowX | Warning | Poll interval outlasts the poll's own timeout — a PollUntil whose first gap is longer than its budget wakes past it, so the loop is one attempt followed by the OnTimeout block and reads in a journal exactly like a dependency that never answered. Silent when either duration is one the compiler cannot fold. [Documentation](https://github.com/votrongdao/FlowX/blob/master/docs/diagnostics/FLOWX1043.md)
FLOWX1044 | FlowX | Error | PollUntil requires an idempotent capability — a poll invokes its capability once per attempt with one request's worth of input and one idempotency key, which is the repetition Idempotent = true declares to be safe and the same promise FLOWX1014 requires of a retry. [Documentation](https://github.com/votrongdao/FlowX/blob/master/docs/diagnostics/FLOWX1044.md)
FLOWX1049 | FlowX | Error | Stream lateness, checkpoint or parallelism cannot be read — a [StreamTrigger] whose Lateness or Checkpoint is not a non-negative ISO-8601 duration, or whose Parallelism is below one. The three are StreamWindowSpec.Read's other arguments, which FLOWX1042 does not judge; FlowStreamCatalog.Add throws on them at composition time, so the deployment finds out from a pod that never becomes ready over values that were compile-time constants the whole way. [Documentation](https://github.com/votrongdao/FlowX/blob/master/docs/diagnostics/FLOWX1049.md)
FLOWX1050 | FlowX | Error | Step binds a contract only one of a poll's two endings produces — a PollUntil declaring .OrSignal<TSignal>() leaves its wait either because the predicate held over an attempt's result or because a delivery seeded TSignal, and both continue at the same step. A step after it binding TSignal runs on the delivery path and throws on the predicate path, which is the path a poll exists for. [Documentation](https://github.com/votrongdao/FlowX/blob/master/docs/diagnostics/FLOWX1050.md)
FLOWX1051 | FlowX | Error | Trigger decoder does not produce the flow's input — a payload-bearing trigger may name a Decode instead of forcing the flow to take the payload, and FLOWX1038, FLOWX1039, FLOWX1041 and FLOWX1042 stand down when it does. They can only stand down if the named type implements ITriggerDecoder<TPayload, TIn> for this trigger's payload and this flow's input; anything else leaves the gap they were closing under a declaration that reads as handled. [Documentation](https://github.com/votrongdao/FlowX/blob/master/docs/diagnostics/FLOWX1051.md)
